# モバイルの LCP を 2.5秒未満にする（2026-11-07）

## 問いと結論

- **問い:** Rust に置き換えることで、モバイルの LCP（2.71〜2.95秒）を基準の 2.5秒未満にできるか。
- **結論:** Rust には置き換えない。遅れの原因はサーバーの速さではなく、最初の画面までに通信を順番に待つ回数と、そのとき読むバイト数だった。どちらも Rust にしても減らない。往復を減らし、読むバイトを減らす直しで、5画面すべてが 2.5秒未満になった（下の「結果」）。

## 測り方

- `scripts/lighthouse-real.mjs`: `dist-http` と `server/dev.ts`（見本の家族）を手元で動かし、サインインした状態で Lighthouse 12.8.2 を流す。画面と形（モバイル・机）ごとに3回測り、LCP の中央値の回を残す。結果は `docs/audits/lighthouse/`。
- モバイルの条件は Lighthouse の既定の模擬（Lantern）。RTT 150ms、1.6Mbps、CPU 4倍。Lantern は、手元で実際に読み込んだ記録（通信の依存とメインスレッドの仕事）を、この条件の回線と CPU に当てはめて時間を見積もる（根拠の強さ O: Lighthouse の公式の説明）。
- 手元の配信（`vite preview`）は HTTP/1.1。本番の nginx は HTTP/2 なので、本番より厳しい条件で測っている。

## 直す前の時間の内訳（今日の画面）

- LCP の要素は、見出しの下の説明文（`p.lede`）。データに関わらない固定の文だが、画面の部品とデータがそろうまで描かれない。
- LCP 2,714ms のうち、最初の応答（TTFB）が 452ms、描くまでの待ち（Render Delay）が 2,262ms（83%）。
- 通信は次の順に、前のものを待ってから始まっていた。
  1. HTML
  2. 入口の JS（67KB）と CSS（20KB）と、入口が読む11の小さなファイル
  3. `runtime.http`（入口が動いてから読む）
  4. `GET /v1/auth/session`（画面を描いてから）
  5. `GET /v1/households/current/snapshot`（4 の後）
  6. 今日の画面の部品と、それが読む6つの小さなファイル
- LCP より前の要求は30本、約196KB。書体（Noto Sans JP の英字の部分、26KB）、通知・版の確認・プライバシーの設定も、LCP より前に始まっていた。
- サーバーの応答は数 ms で、遅れにはほとんど関わっていない。

## Rust を使わない理由

| 案 | 見込み | 判断 |
|---|---|---|
| API を Rust（axum など）で書き直す | サーバーで使う時間は1つの要求で数 ms。模擬の回線では1回の往復が 150ms 以上かかるので、縮むのは全体の1%未満。認証・監査・バックアップ・同等性の試験をすべて作り直す危険が大きい | 採らない |
| 画面を Rust と WebAssembly（Leptos・Dioxus など）で作る | WebAssembly のファイルを読んで準備する分が加わり、最初の表示までのバイト数はむしろ増えやすい。全画面と、画面の試験（Chromium と WebKit で約2,000件）を作り直すことになる | 採らない |
| サーバーで最初の画面を描く（SSR） | 効く。ただし Rust でなくても、今の Node と React の `renderToString` でできる。変更が大きいので、下の直しで届かなかったときの次の手として残した | 今回は不要 |

## 行った直しと、それぞれの効き目

今日の画面のモバイル（1回ずつの測定）。

| 直し | LCP | 理由 |
|---|---|---|
| 直す前 | 2,714ms | — |
| HTML の中の小さなスクリプト（`boot-*.js`）で、セッションと家族の記録の取得、開いた画面の部品の先読みを始める（`src/app/bootPrefetch.ts`、`src/app/bootFetch.ts`、`vite.config.ts` の `bootPrefetch()`） | 2,714ms | 順番待ちはなくなったが、すべての要求が同時に始まり、回線を取り合うので、模擬の時間は変わらなかった |
| （試し）書体をやめる | 2,576ms | 26KB の分だけ早くなる |
| 入口が最初に読む部品を1つのファイルにまとめる（Rolldown の `codeSplitting.groups` の `$initial`） | 2,426ms | HTTP/1.1 では同時に6本しかつなげず、小さなファイルが多いと往復を待つ。LCP より前の要求が30本から19本に減った |
| `runtime.http` を入口に入れる。通知と版の確認を、画面を描き終えてから取りに行く（`src/app/afterPageLoad.ts`） | 2,408ms | 最初の画面に要らない要求を、LCP の後へ回した |
| プライバシーの設定を、家族の記録と一緒に取って一緒に反映する | 2,411ms | 別々に反映すると画面全体を2回描き直し、予定の画面で長い処理が増えて点数が 84 に下がっていた（91 に戻った） |
| 英字の書体もやめ、端末のゴシックにする（`docs/design/tokens.md` の (c)） | 2,261ms | 最初の表示で読む woff2 が0になった |
| HTML に読み込み中の画面を入れる（`index.html`、`src/app/staticShell.test.ts`） | 2,263ms | 模擬の LCP は変わらない。実際の端末では、JS を読む前に画面が出る |
| 先読みのスクリプトを `async` にする | — | HTML の読み取りと最初の描画を止めない |

ほかに試して採らなかったもの:
- 2つ以上の画面が使う部品を1つにまとめる: まとめたファイルが 49〜68KB になり、どの画面でも余分に読むので採らなかった。

途中で見つけて直した不具合:
- 入口を1つにまとめたことで、入口の top-level await が後から読む部品と互いに待ち合い、モックのビルドが白い画面のまま止まった。top-level await をやめた（`src/main.tsx`）。
- top-level await をやめたことで、service worker が登録されるようになった。前は、await の後に `load` を待つ処理を足していたが、そのときには `load` が過ぎていて、登録されていなかった（main のビルドで登録の数が0であることを確かめた）。登録されると、画面の部品は service worker が取るので、部品を差し替える画面の試験（FRAME-3、ILLUS-1 のエラー、色の対比、撮影の route-error）では service worker を止めた。登録されることは `e2e/shell.spec.ts` の new-version notice で確かめる。service worker は `/v1/` を扱わないので、写真や添付は端末に残さない。

## 結果（3回の中央値）

`node scripts/lighthouse-real.mjs --runs 3 --check`（2026-11-07）。数値の元は `docs/audits/lighthouse/`。

| 画面 | モバイル LCP（前 → 後） | FCP（前 → 後） | Performance | Accessibility | Best Practices | CLS | 机の LCP（前 → 後） |
|---|---|---|---|---|---|---|---|
| 今日 | 2,714 → **2,262ms** | 2,180 → 1,654ms | 94 → 98 | 100 | 100 | 0 | 610 → 527ms |
| 予定 | 2,730 → **2,410ms** | 2,260 → 1,728ms | 93 → 91 | 100 | 100 | 0 | 612 → 567ms |
| 家計 | 2,730 → **2,407ms** | 2,333 → 1,804ms | 93 → 97 | 100 | 100 | 0.0156 | 651 → 567ms |
| アルバム | 2,952 → **2,406ms** | 2,332 → 1,729ms | 92 → 97 | 100 | 96（見本の写真のファイルがない 502。前からの例外） | 0 | 650 → 566ms |
| メモ | 2,732 → **2,406ms** | 2,335 → 1,804ms | 93 → 97 | 100 | 100 | 0.0156 | 654 → 566ms |

- 5画面ともモバイルの LCP の中央値が 2.5秒未満、CLS 0.1未満、Accessibility 100。机は5画面とも Performance 100。
- 3回の幅は最大で 158ms（メモの1回目が 2,253ms）。ほかは 10ms 以内。
- 予定の画面の Performance は 91 で、基準（90 以上）に近い。月の表を描く処理が長く（TBT 約 280ms）、描き直しの回数を減らす余地がある。
- 基準との余裕は約 90ms。画面の部品や最初に読む CSS（19KB）が増えると超えうる。`scripts/lighthouse-real.mjs --check` を変更のたびに流す。

## 確かめていないこと

- 実際の端末と回線での LCP（フィールドのデータ）。Lantern は模擬で、実際の 4G の端末の値とは違う。
- 本番の構成（nginx の HTTP/2 と gzip_static）での Lighthouse。手元の HTTP/1.1 より有利になる見込みだが、測っていない。
- Firefox。
